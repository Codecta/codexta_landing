Most enterprise AI deployments bolt a chatbot onto one system and call it done. Codexta doesn't.

In a single conversation it can look up a customer record, search your knowledge base, trigger a transaction, escalate a case, generate a report, and remember the outcome next time — learning how your organization works along the way, scoped strictly to the domains and data you authorize. It's not a chatbot. It's the operating layer for your enterprise's day-to-day work.

Why Codexta

Every enterprise agent hits the same wall. Here's how we get past it.

✕ WHAT USUALLY BREAKS AT SCALE

Stack every policy into one system prompt and it degrades — the banking rules crowd out the retail rules crowd out the support rules, and the model starts quietly ignoring instructions nobody meant to bury.

Build a routing graph instead and you've traded prompt overload for a maintenance problem: every new case is an edge a developer has to hand-wire, and the graph gets more brittle with every branch you add.

✓ WHAT CODEXTA DOES INSTEAD

No giant prompt, no graph drawn in advance. Each task loads exactly one guideline — the rules and tools for that domain, nothing else. When a request crosses into a second domain, Codexta spawns an isolated child task for it on the spot, passing forward only the specific facts that task actually needs.

A guideline is a document, not code — scope, rules, execution steps, presentation rules. Reaching a new domain means writing one (see Business Processes, below), not re-architecting a graph or re-tuning a mega-prompt.

And it can only do what a loaded guideline explicitly authorizes. There's no ambient "do whatever the user asks" mode — if a tool or action isn't scoped into the guideline for that task, Codexta has no way to reach it, no matter how the request is phrased. For a business putting an agent in front of real customers and real systems, that boundary is the whole point.

To be clear about what that does and doesn't mean: Codexta isn't a claim that one model can handle anything you throw at it. It ships today with a defined set of domains — the flavors below — and each one only does what its guideline actually authorizes it to do. Reaching the next one is fast. It still has to be reached.

05 · Lane Discipline

It only does what you gave it a guideline for.

Ask it to write you a song, tell a joke, or chat about the news, and Codexta declines — not because a filter caught a bad word, but because no loaded guideline covers it. Scope is a strict allow-list, not a blocklist: if a domain wasn't authored for this deployment, the request has nowhere to run.

That's the same mechanism that keeps banking tools out of a shopping task — it's just as strict at the edge of the whole system as it is between domains inside it. You decide exactly what your deployment can do; nothing more is reachable by asking nicely.

07 · Learns From Mistakes

Corrected once. Right from then on.

Correct Codexta on a fact — a wrong return window, a stale API version, a step it skipped — and it doesn't just fix the answer in front of you. It writes the correction down as a lesson, tagged to the domain it belongs to, so the next task that touches the same ground finds it before making the same mistake.

If a stored lesson turns out to be stale itself, Codexta corrects the note in place instead of quietly working around it — a memory that's wrong once shouldn't keep being wrong.

10 · Business Processes

A new onboarding flow or an incident process is a conversation, not a sprint.

Underneath every domain Codexta handles is a guideline — a single readable document with a scope, a set of rules, an execution workflow and presentation rules, exactly like the ones running this deployment right now: incident_report.md and shop_onboarding.md. A business process here isn't code somebody deploys — it's a document Codexta itself writes, wires to real tools, tests, and puts into effect.

Tell it the registration flow needs a date-of-birth field only when the API demands one, or that escalations above £500 need a second approval, and it edits the process definition and rewires the tools that already exist — nothing goes live until you say so, and every prior version is one click from being restored.

That's the difference between a chatbot with an FAQ and a platform that runs your business's actual procedures — onboarding, incident handling, order fulfilment, escalation policy — each one a living document your team can read, correct, and hand back to the agent to keep running.

11 · Process Enforcement

Modeling the process isn't a suggestion. It's a lock.

A guideline's PROCESS block — the state machine describing how a business process actually runs — isn't just instructions the model tries to follow. Codexta compiles it into a real graph and checks every relevant tool call against it at runtime: is this transition legal from the current state, is this tool even callable here, did the required steps fire in the order the process demands.

A call that breaks the rule isn't discouraged — it's denied before it executes, with the exact reason and the exact next step handed back, so the model corrects itself instead of quietly skipping ahead. Scope stays narrow on purpose: only the tools the process itself names are governed — a workflow can never accidentally lock up the rest of the runtime.

This is the difference between an agent that's told never to finalize an application without approval, and one that structurally can't — because the check lives in code compiled straight from the process a business owner described, not in a prompt the model has to remember to obey.

product.md · PROCESS "Apply for product" · current state: PRODUCT_DRAFT_STATE
product_set_state(state="PRODUCT_FINALIZED")
✕
illegal_transition from=PRODUCT_DRAFT_STATE to=PRODUCT_FINALIZED.
Allowed from 'PRODUCT_DRAFT_STATE': PRODUCT_APPROVED_STATE, PRODUCT_CANCELED.
Nothing was changed.

✓ method validity — a tool only callable in the states that actually name it

13 · Security

Passwords the model never sees.

When a user signs in, registers, or authenticates, the password never reaches the language model in plain text. It's encrypted the moment it's entered, held in session-only memory, and used at the real value the model never has access to.

Sealed end-to-end — closing an entire class of prompt-injection and credential-leak risk that affects most agent platforms today. Every action is written to an immutable audit log, access is scoped by role, and — because the model can run self-hosted — nothing has to leave your network boundary.

14 · Cost Efficiency

The engineering is in the prompt, not the model bill.

Most agent frameworks need a frontier model to stay reliable — the reasoning has to compensate for a thin, generic system prompt. Codexta pushes that work the other direction: task-frame isolation, strict guideline gating, and per-domain tool loading are load-bearing engineering, not decoration, so a smaller, cheaper model can drive the same workflow just as reliably.

That's what makes a self-hosted Gemma 4 or DeepSeek deployment realistic in the first place — running on infrastructure you already pay for, with no per-token bill and no data leaving your network, instead of routing every turn through a premium API.

These budgets aren't theoretical — they're tuned against real traces. One run held 198,901 characters of stale file context in a single task, pushing turns to ~85K tokens and the whole run to 4.95M; a retry loop with no bound burned ~130K tokens per attempt across 20+ turns. Both became permanent, bounded fixes — not patches.

16 · How It Compares

Built for a different job than a code CLI or a chat window.

LangChain/LangGraph is the closest peer on raw orchestration — its graph model genuinely covers task dependencies well, though that graph is authored by a developer at build time; Codexta's task graph is invented by the model itself, on the fly, per conversation. Parlant is the closest peer on the core idea — its "guidelines" are contextually-matched behavioral rules too — but they're developer-authored constraints on one agent's dialogue, not a system that spins up isolated domains and writes its own tools, UI and business processes. Kore.ai and similar enterprise IVA platforms solve real production problems — some, like drop-in embed widgets and document search, ahead of Codexta today — through no-code flow design at build time, not an agent that invents its own task graph and process definitions live. Claude Code and ChatGPT solve different problems (a coding CLI, a general chat product), so several rows below don't apply to them at all — marked as such rather than scored as a loss for a category they were never built for.

Task orchestration

Each task sees only what it needs to.

Codexta splits every request into isolated task frames. Each frame loads only its domain tools and the exact context that step requires — then passes a single result back. No bloat, no bleed-through, no contamination between domains.

Under the hood
Not a growing chat log — a state snapshot, rebuilt every turn

Most agent frameworks keep one transcript and replay the whole thing every turn — every tool call that ever ran stays in there, and "the current state" is whatever the model can infer from the last matching mention buried in it. Codexta doesn't work that way. Every turn it rebuilds the message from scratch, in a fixed order — guidelines, then preferences, then context, then the turn-by-turn trace — and a tool call that changes something doesn't add a new line to a growing history. It overwrites the one live snapshot for that entity, in place.

Rebuilding the message every turn sounds like it should cost more, not less — but the layout is deliberate: guidelines and preferences (rarely change) sit at the top, context (changes slowly) in the middle, the live trace (changes every turn) at the bottom. Everything above the line that just moved is byte-for-byte identical to the previous turn, so the model's prompt cache still serves it — 95%+ of input tokens hit cache in practice, not just on the first reply of a session.
